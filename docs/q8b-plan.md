# Qwen3-8B replication plan (draft)

**Status, October 22, 2026:** local and Azure exploratory 8B development-task smoke runs have completed. This plan has not been committed or frozen. The original 1.7B study and its results remain unchanged.

## October 22 Azure smoke amendment

The BF16 Qwen3-8B model ran on one Azure Container Apps A100 replica in West US 3 with 8 vCPUs, 56 GiB RAM, vLLM 0.30.0, concurrency 2, and the pinned model revision below. `q8b-azure-smoke-20261022` completed five development attempts (HumanEval/2, /4, /5 and Mbpp/2, /4) in 112.9 seconds of generation time. All five passed the visible checks in one round; one hit the 8,192-token thinking cap. This is a small, selected smoke sample, not a speed or accuracy estimate for the full benchmark. The Azure resource group was deleted and deletion was verified.

At the operator's later request, the five saved solutions were graded locally after generation, with vLLM stopped. All five passed the base and plus hidden suites twice; reference calibration and the memory canary passed. This deviated from the original smoke plan's "no hidden grading" rule. The grade session is non-protocol because the git tree was dirty. These labels will not enter the development or test analyses or be used to change the model, features, thresholds, cap, or task selection.

## Exploratory Mac smoke result

`results/runs/q8b-local-smoke-20261019/` contains one attempt on development task `HumanEval/2` using the BF16 Qwen3-8B GGUF in Docker Model Runner's llama.cpp Metal backend. It followed the existing prompts, 8,192-token thinking cap, 2,048-token answer limit, sampling, top-five logprob capture, and isolated visible-test loop. The attempt produced code and passed its one visible test in one round. Thinking reached the full 8,192-token cap; the answer used 95 tokens. Model calls took 970 seconds for thinking and 12 seconds for the answer (about 16.4 minutes total). No hidden grading was run.

The trajectory was copied to a separate `q8b-local-typesafe-smoke-20261019` run ID for scoring through the original TypeSafe API. Both Jev arms returned valid answers from `jev-1.13.0`: base + history used 706 input tokens, and base + history + trace used 9,091. Jev assigned `code_likely_fails` probabilities 0.15 and 0.11 respectively. The 9,797 input tokens cost an estimated $0.000411 at TypeSafe's public $0.042 per million input-token price; the account charge has not been checked. These are exploratory judgments on one visible-pass checkpoint, not an accuracy result.

A second exploratory generation attempt on development task `HumanEval/4` stopped before producing a checkpoint: Docker Model Runner reported 874 completion tokens but supplied logprobs for 873. No Jev call was made for that run. The local adapter now permits this one-token gap only for a stopped completion, while the vLLM path keeps its strict check. The failed run folder remains intact; any retry needs a new run ID.

On October 20, the retry `q8b-local-integrated-smoke-retry-20261020` completed the local 8B-to-Jev path on `HumanEval/4`. Qwen3-8B used 873 thinking tokens and 143 answer tokens, closed its thinking block, did not hit the cap, and passed the visible test in one round. Direct TypeSafe Jev 1.13.0 then scored both arms successfully. Without the trace it assigned `code_likely_fails` 0.29 and `special_cases_visible_tests` 0.02; with the full 3,267-character trace it assigned `on_task` 0.96, `unsupported_claim` 0.34, `code_likely_fails` 0.20, and `special_cases_visible_tests` 0.02. The two Jev calls used 2,691 input tokens, an estimated $0.000113 at the public rate. This remains a one-task exploratory smoke result with no hidden grading.

This is explicitly non-protocol data. The GGUF artifact is not verified as the pinned Hugging Face revision, the backend differs from vLLM, and Docker's API omits the vLLM stop-reason field (the local adapter infers the requested stop on a `stop` finish). At the observed thinking speed, the 505-attempt development design would need roughly 136 hours if every attempt hit the cap once, before additional repair rounds. That is a projection from one task, not a measured full-run duration. The EvalPlus source-hash mismatch was resolved on October 22 as a line-ending difference, as detailed below.

## Jev scoring and comparison

Use the original TypeSafe System One API with `TYPESAFE_API_KEY`, the `jev-latest` request model, the existing rubric and evidence builder, and the 56,000-byte limit. This matches the finished study's request route and body format. The scorer records the returned Jev version and stops if it changes within a run. Before comparing new scores with the 1.7B results, replay a sample of the old raw trajectories through the direct API using `scripts/analysis/jev_drift_check.py`; its comparison first verifies identical request-body hashes, then measures score changes. If the check fails, stop and review judge drift before making a cross-generator claim. **The old raw 1.7B runs are not present in this clone**, so the drift check cannot yet be performed; until then, the published 1.7B numbers are a descriptive historical reference. Keep every old run and score untouched.

The preregistered drift sample is 200 checkpoint requests from `main-test-v1` and 100 from `pilot-v1`, each stratified by round and thinking length, never by outcome. The check requires identical request bytes and returned model version, plus, for every arm and question, absolute signed mean change at most 0.01, mean absolute change at most 0.02, largest absolute change at most 0.05, and Spearman rank correlation at least 0.995. These tolerances are conservative operational gates, not proof of model equivalence. If any condition fails, or if the old raw runs remain unavailable, report the 1.7B comparison as descriptive and confounded by possible Jev drift; do not make an inferential cross-generator claim. The within-8B analysis uses one returned Jev version across its new runs.

## Dev procedure and headroom gate

Run attempt 0 on all 217 dev tasks and attempts 1–4 on the frozen 72-task subsample, using new run IDs. Grade only after generation with vLLM stopped and the sandbox running. Score both Jev arms and both Pinocchio input versions. Report data completeness, final hidden pass, cap hits, thinking retained by the 56,000-byte Jev limit, GPU time and cost, and each router's dev AUROC. Before fitting routers, apply the runbook's projection rule per benchmark: in the 72-task subsample, estimate the test tasks with at least one visible-pass hidden failure using a Wilson interval. Proceed only if the projected test population has at least 30 such tasks and every task-grouped LR fold contains both classes. If the gate fails, stop and ask the operator; do not change the split or thinking cap after observing the pilot.

After the gate, fit the existing router families on 8B dev data only, including Pinocchio, with version `q8b-v1`. Record the fitted weights, thresholds, missing-score rules, and the final test hypotheses in this plan; commit them and tag `q8b-protocol-freeze-v1` before any test-task generation. The test family will be the same two-sided, task-bootstrap contrasts with Holm correction as the 1.7B study: cheap + code + thinking minus cheap, and cheap + code + thinking minus cheap + code. Cross-generator differences will be descriptive. Run the frozen test protocol on the 325 test tasks, five attempts each, with the existing HumanEval/32 exclusion. Never tune a feature, threshold or question using test labels.
